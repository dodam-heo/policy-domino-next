# 정책도미노 NEXT — 제출용 소프트웨어 설계·품질 기준

## 목적과 검증 범위

정책도미노는 특정 정책 하나에 반응하는 예제 프로그램이 아닙니다. 대한민국 공공부문의 새로운 법령·행정규칙·자치법규 등 **어떤 규범의 변경이든** 공적 근거를 바탕으로 수집하고, 실제 전후 문구를 비교하고, 영향을 받는 하위 규정·기관 업무·공공사업·검토 조치를 추적하는 범용 시스템입니다.

**특정 사례의 정답을 코드에 심거나, 기관명을 사전 등록하거나, 사용자가 지적한 사례에 맞춘 if/else를 누적하는 방법으로 구현하지 않습니다.** 직제 변경은 이러한 규범 변경 중 하나일 뿐입니다. 금액·자격·절차·기간·서식·권한·폐지에도 동일한 분석 단계를 적용합니다.

## 1. 모듈별 소유권과 입력·출력

| 모듈 | 입력 | 핵심 책임 | 출력 |
|---|---|---|---|
| api | 공식 API 매개변수 | 공식 문서 발견, 버전 및 페이지 수 확인 | 출처가 명시된 원천 문서 |
| parser | 공식 XML 원문 | 조문·부칙·별표를 공통 단위로 정규화 | 누락·잘림 표시가 있는 조항 |
| analysis | 동일 문서의 과거·현재 조항 | 실제 변경 내용·숫자·인용 증거 추출 | 차이 및 근거 |
| discovery | 변경 조항 및 공식 문서 원문 | 다른 규정과의 공적 관계 탐색 | 입증된 관계와 미검증 후보 |
| hierarchy | 관련 규정 간 인용·위임 | 법령의 관계 유형 해석 | 법적 검토 경로, 적용 확정 아님 |
| **후속 기관업무 엔진** | 공식 기관·사업자료 | 실제 사업 기준과 정책의 연결 검증 | 기관별 검토사항 및 원문 근거 |
| pipeline | 단계별 결과 | 한 개의 운영 순서·재시도·정책 이벤트 조정 | 일관된 상태·공개 데이터 |
| contracts | 공개 데이터 | 주장된 검증 상태와 실제 증거 일치 확인 | 통과·차단 |
| site/index.html | 페이지 구조 | 의미론적 화면 구조만 정의 | 접근성 구조 |
| site/styles.css | 디자인 | 모바일·PC의 레이아웃과 시각체계 | 일관된 표시 |
| site/presentation.js | 공개 계약 | 최신 변경 우선 목록, 사업 적용 검증·수행주체 후보를 분리하는 순수 함수 | 화면 전용 결과 모델 |
| site/app.js | 공개 계약 및 화면 전용 결과 모델 | 목록·상세·비교·기관 선택 화면 제어 | 사용자 인터랙션 |

규범을 비교하는 알고리즘이 HTML 구조를 직접 다루어서는 안 되며, 화면 코드가 공식 조문을 새로 해석하거나 미검증 조치를 만들어서도 안 됩니다.

## 2. 독립적인 증거 단계

**공식 문서 발견 → 종전/현재 조문 실제 변경 → 공식 규정 간 적용·위임·인용 관계 → 공공기관 사업 운영 근거 → 기관별 변경 검토사항 → 실제 이행 여부**.

각 단계에서 요구하는 출처는 다릅니다.

- *공식 목록*: 법제처의 ID, 공포·발령일, 버전, 공식 URL.
- *내용 확인*: 공식 이전·현재 원문과 비교 위치 및 양쪽 원문 해시.
- *규범 연결*: 하위 규정에 적힌 인용, 위임, 적용 범위, 실제 연결 조문.
- *기관·사업 연결*: 공공기관이 발표한 사업 운영기준과 그 조문의 직접적 관계.
- *검토사항*: 무엇이 이전과 달라졌고 기관의 어떤 업무·기준에서 왜 검토가 필요한지의 근거.
- *이행 완료*: 공식적으로 후속 조치를 확인한 자료.

관계가 확인되지 않은 경우는 미검증이며, 거짓으로 빈 영향이나 최종 조치로 바꾸면 안 됩니다. **발령기관·소관부처라는 사실만으로 실제 집행기관을 만들지 않습니다.**

## 3. 저장 구조 개선 목표

현재 운영 중인 `data/state.json`과 `site/data.json`은 크기가 커지고 있으며, 단일 파일 전체를 덮어쓰는 구조는 안정성·속도·Git 이력에 좋지 않습니다. 이 문제는 데이터를 잘라 버리는 방식으로 해결하지 않습니다.

목표 구조:

1. 개정 사건 색인: ID, 제목, 공포일, 검증 상태, 독립적 근거 수만 포함하는 **작은 목록 데이터**.
2. 상세 내용: 실제 변경된 조문 단위의 **지연 조회 가능 자료**. 긴 원문·별표는 별도 자료로 보존.
3. 내부 상태: 다운로드 작업, 오류, 재시도, 문서 버전, 검색 범위를 **증분 보관**. 필요하면 SQLite나 파일 단위 저장으로 전환하고 Git에는 검증된 공개 결과만 반영.
4. 공식 증거: 공식 URL, 원문 발행일, 본문 해시, 정확한 조문·문구를 버전과 함께 기록.
5. 데이터 생성과 화면 배포의 일관성을 보장하고 실행 취소·중복 배포 시 이전 데이터로 덮이지 않도록 검사.

현재는 **이 저장 방식 전환을 아직 구현하지 않았습니다**. 설계 작업을 완료하고 동일 데이터의 재현 테스트를 확보한 다음 이관합니다.

## 4. 기능별 제출 승인 게이트

| 기능 | 통과 조건 |
|---|---|
| 수집 | 전 원천별 실제 총건수·수집건수·누락 페이지·조회 오류를 재현 가능하게 기록 |
| 조문 비교 | 변경되지 않은 부분은 미표시, 변경 부분만 강조, 이전·현재 원문은 언제든 확인 가능 |
| 법적 관계 | 직접 인용·위임·적용 관계를 **서로 구별**하고 해당 문서·조항으로 입증 |
| 공공기관·사업 | 사전 등록되지 않은 기관과 사업을 실제 운영 자료에서 동적으로 찾아 연결 |
| 기관별 조치 | 기관·업무의 실제 적용 위치와 변경 전후를 함께 제시하고 근거 부족은 미확인 |
| 범용성 | 금액·자격·기한·절차·조직·권한·신규·개정·폐지 등이 모두 같은 엔진 통과 |
| 코드 | 원천/분석/데이터/웹 분리, 타입·스키마 검증, 함수 단위 테스트, 단일 자동 실행 경로 |
| 웹 | 모바일 목록→상세→뒤로, 조문 요약 및 전체 보기, **기관 이름별 필터**, PC 표시 통과 |
| 배포 | 모든 자동 테스트 + 공개 근거 계약 통과 후 GitHub Pages 게시 |
| 품질평가 | **새로운 실제 정책 사례**에 대한 정확한 변경 판별·인과 연결 정밀도·미발견률 측정 |

기관별 검토사항에는 사업 적용 관계가 공식 근거로 검증된 경우만 확정 조치 후보로 표시하며, **조문에 인물이 등장하거나 규정이 인용했다는 사실만으로 기관의 수정 업무를 자동 생성하지 않습니다.**

특정 부처의 직제 개편이나 특정 급여 고시만 정상적으로 보이는 것은 통과 기준이 아닙니다. 비교 데이터는 여러 분야에 걸쳐 독립적으로 선정해야 합니다.

## 5. 현재 코드 상태와 남은 구조적 과제

### 현재 반영
- 프론트엔드의 HTML/CSS/JavaScript 파일 분리 및 순수 프레젠테이션 모델 별도 모듈화
- 최신순 공식 변경 목록을 기본으로 복원하고, 기관별 검토에서 **사업 적용까지 검증된 조치**와 **조문상 수행주체 후보**를 분리
- 분석의 중간 지표는 초기 화면에서 제거하고 추가 인용·수행주체 정보는 접힌 상세 근거로 제공
- 풀 리퀘스트에 대해 배포 권한 없이 자동 회귀 테스트를 실행하고, 메인 배포는 테스트 통과 후 진행
- 공개 데이터 근거 계약을 수집 결과 생성과 배포 전에 공통 검증
- 발령기관·조문 인용을 실제 사업 조치로 오인하는 결과를 차단하는 자동 테스트
- 유일한 운영 파이프라인, 단일 GitHub Actions 워크플로

### 아직 미완성
- 기관 공식 사업자료를 자동 발굴·재조회하는 범용 연결 엔진
- 모든 하위 규범의 관계를 전수 발굴하는 충분한 원천 커버리지
- 데이터 목록/상세의 분할·지연 조회 및 내부 상태의 증분 저장

**기능을 화면에 표시하는 것과 신뢰할 만한 자동 영향 분석을 완성하는 것은 다른 단계입니다.**
