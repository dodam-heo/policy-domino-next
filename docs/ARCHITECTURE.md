## 공공기관별 결과 확인과 색인 문서 검색

정책 상세 화면의 **기관별 변경·사업 검토사항**에는 두 종류의 근거를 하나의 기관명 필터로 탐색할 수 있다. ① 개정 조문 자체에 명시되거나 공공기관 직제·공식 인용으로 추적되는 변경 조문별 업무 검토, ② 정부24 공식 서비스 ID·기관명·사업 운영기준·법령 인용이 맞는 실제 공공서비스의 기준 검토 후보. 각 자료의 근거 수준은 유지하며 후보를 조치 의무/반영 완료로 취급하지 않는다. 기관·서비스 이름을 코드에 등록하거나 특정 분야의 예상 영향을 주입하지 않는다.

특히 **기관 자체의 '○○ 직제'와 '○○와/과 그 소속기관 직제(시행규칙)'**는 공식 법령 제목으로 실제 규율 대상을 특정할 수 있을 때만 기관별 검토에 연결한다. 인원·금액·업무 기준의 신구 실제 변경 조각은 해당 기관의 검토 문장과 별도 출처에 표시한다. 여러 법령의 공포번호가 같다는 이유만으로 기관·조문을 합치지 않는다.

새로운 정책 변경을 확정한 문서만 보여주는 본 목록은 유지한다. 검색어를 입력하면 추가로 **공식자료 검색 · 분석 대기 포함**을 펼쳐 공식 색인에 이미 있는 미분석 고시·행정규칙·법령을 확인할 수 있다. 이 자료는 등록 여부·종전/현행 본문 확보·분석 대기 상태를 보여주는 것이지 이미 확인된 개정 사건은 아니다. 자료가 아직 색인되지 않았다면 자동으로 가상의 고시나 기관·사업을 생성하지 않는다.

# 정책도미노 NEXT — 정책 사건 중심 단일 아키텍처

## 1. 분석 대상·제품 정의

정책도미노는 정부의 규범·지침 변화가 **공공기관의 어느 업무·사업·운영기준에 파급되는지**를 공식 근거로 연결해 사용자에게 변경 검토사항을 제공한다. 대상은 중앙부처·지자체·교육청·공공기관을 포함한 공공조직이며 민간조직은 기관별 분석에서 제외한다.

**원천 색인(검색 결과)과 정책 변경 사건을 동일시하지 않는다.** 수천 개 문서가 수집되어도 신구 원문 비교나 신규 제정·폐지 확인이 끝나지 않았다면 사용자에게 '변경 사건'으로 노출하지 않는다.

## 2. 유일한 프로덕션 흐름

```
LawAPI official IDs / promulgation number / date / instrument type
  │
  ├─ api.py + parser.py     → documents and complete versions
  ├─ analysis.py            → source-confirmed change clauses (before, after, SHA)
  ├─ discovery.py           → exact article citations in other official rules
  └─ alioplus.py/programs.py→ exact public program citations and provenance
                              │
                              ▼
                    events.build_events()
           official document identity -> policy event
           changed clause -> regulated institution
           changed clause -> explicit changed-clause actor
           exact article -> cited public program / subordinate rule
                              │
                    optional ai.analyze_batch()
             source-anchored supplementary review only
                              │
                   contracts.validate_public()
                              │
                   pipeline.render() → site/data.json
                              │
                presentation.js / app.js / index.html
```

운영 명령은 `python -m policy_domino {run,ai,ai-check,render}`이며 GitHub Actions 워크플로는 `.github/workflows/pipeline.yml` 하나다.

## 3. 데이터 엔터티와 식별자

| 엔터티 | 식별 | 상태 |
|---|---|---|
| OfficialDocument | 원천 종류 + 법령 ID + 버전 일련번호 | 색인/원문 검증 |
| ChangedProvision | document ID + 조문 번호 + 신구 원문 SHA | 실제 변경이 확인된 조문 |
| PolicyEvent | 검증된 개별 변경 문서의 ID(법령당 1건) | 검증된 법령별 변경 사건 |
| InstitutionalReview | 문서 ID + 변경 조문 + 근거로 확인된 기관 + 사업 ID + 근거 등급 | 기관 업무의 검토 대상 |
| LegalCitation | 변경 조문 + 인용한 다른 규정의 명시적 조문·인용문 | 법령 관계 증명, 사업 조치 아님 |
| AIDraft | 원문 SHA + 모델 + 검증된 변경·기관·사업 ID | 공개 근거에 따른 보조 검토 |

**사건 격리:** 모든 중앙 법령·행정규칙·지방자치법규는 원천 변경 문서 ID별로 개별 사건을 만든다. 공포번호·공포일·종류가 동일한 일괄 개정도 서로 다른 법령의 신구 조문과 기관을 합치지 않는다. 공통 공포 이력은 필요시 별도 연결 메타데이터일 뿐 사건 합병 조건이 아니다. 제목 유사도·특정 정책명·기관명·업권으로도 그룹을 강제하지 않는다.

`events.py`는 수집 상태를 덮어쓰지 않고 현재 원천·분석으로부터 사건을 **결정론적으로 재생성**한다. 여러 문서의 원문과 이력은 그대로 보존하고, 사용자 목록은 `events[]`를 기준으로 한다. 기존 저장소의 표시 결과나 legacy 매핑을 읽지 않는다.

## 4. 기관별 업무 영향의 독립적 근거 단계

1. **공식 직무·조직 직접 규율**: 예컨대 공식 규정 제목이 일반적인 `기관명과 그 소속기관 직제` 패턴에 해당하고, 그 규정의 신구 변경 조문을 확보한 경우 그 기관의 관련 운영기준을 **검토 대상**으로 연결한다. 이는 실제 조치 완료 증거가 아니다.
2. **명시적 수행주체**: 변경 조문에서 동일한 수행주체가 전후 원문에 명시되고 변경된 업무 문구가 확인되면 해당 주체의 검토 대상 조문을 제시한다. 조문상 명칭만으로 외부 사업명·내부 시스템을 생성하지 않는다.
3. **공식 사업 연결**: 사업 원문에서 변경 조문을 정확하게 인용하거나, 공식적으로 검증된 중간 규정의 해당 조문을 인용한 경우만 사업명·운영기관·인용문을 연결한다.
4. **관련 규정·추적 단서**: 변경 조문을 인용하는 다른 규정, 단지 규정에 등장하는 수행주체는 확정 사업 검토와 구분하여 근거 상세에서 제공한다.

각 항목은 반드시 `document_id, article, institution, task, basis_tier, source_url, basis_quote`와 실제 확인된 원천을 가진다. 모든 검토사항의 `implementation_status`는 현 단계에서 `not_verified`이다. '기관이 반드시 조치를 완료해야 한다'거나 '미조치 상태다'라고 확정하지 않는다.

기관별 검토사항은 **상위법을 다시 개정하라는 지시**가 아니다. 바뀐 조문이 해당 공공기관 업무의 어느 운영 기준에 적용되는지 확인할 구체적인 위치를 제공하는 것이다. 특정 기관·사업의 수작업 정답 데이터는 없다.

## 5. AI 분석의 역할

`ai.py`는 공식 변경 전·후, 현재 검증된 공공사업 원문과 `events.py`가 생성한 확인된 기관별 검토 후보를 입력으로 받는다. AI의 문구 자체가 영향을 받는 기관을 새로 만들어내지 못한다.

모델의 출력:

- 조문 변경 요약·전후 원문 직접 인용·검토 질문
- 공식 사업의 조문 인용 근거에 한정한 사업 검토 질문
- **이미 증거로 특정된 기관별 검토항목 ID**에 한정한 업무 영향 보조 분석

모델이 생성한 기관 ID, 검토항목 ID, 사업 ID와 원문 인용이 실제 입력에 없는 경우 출력을 폐기한다. 원문 SHA 또는 모델 변경 시 이전 캐시는 무효화된다. `events.py`는 `publishable_draft()`가 검증한 내용만 모아 해당 정책 변경 사건과 기관별 카드에 포함한다.

Gemini 호출은 자료 수집과 분리된 백엔드 작업이며 기본 요청 상한 24회(재시도 포함), 429 중단, 일시 오류 제한 재시도, 요청 시간 상한을 적용한다. `GEMINI_API_KEY`는 GitHub Actions Secret으로만 접근한다.

## 6. 사용자에게 노출하는 구조

첫 페이지의 기본 탐색 객체는 **정책 변경 사건**이다.

- 목록: 법령별 변경 사건 최신순, 해당 법령의 주요 변경·검토 기관 수·검토 업무 수 (공통 공포번호만으로 일괄 병합하지 않음)
- 탐색: **전체 / 신규 / 개정 / 폐지 / 영향도 큼** 5개 빠른 선택 버튼, 정책·법령명·소관기관·사업명 검색, **전체 N건 · 표시 M건** 표시. 별도 변경 항목·기관 연결 드롭다운은 첫 목록에서 제거
- '영향도 큼'은 실제 검증된 기관별 검토사항에서 **서로 다른 공공기관이 2곳 이상** 발견된 경우에만 해당. 사회경제적 파급력 확정·기관 실제 조치 완료를 뜻하지 않으며 근거 미수집 사건의 중요도를 낮게 평가하지 않음
- 상세 첫 영역: 이번 변경의 핵심·신구 핵심 문구·실제 검토 대상 범위
- 그 아래: **기관 이름별로 접을 수 있는** 업무 변경 검토사항·사업 근거
- 원문 상세: 긴 신구 조문·관련 규정·복수 법령 목록은 접어서 열람
- AI: 해당 조문·업무에 연결된 선택적 추가 검토, 공식 변경보다 앞서거나 중심이 되지 않음

'신구 확인'은 내부 원문검증 상태이지, 정책적 의미가 있는 사용자 필터가 아니다. 인상적인 총 수집건수로 AI 분석 완료를 대체하거나 유용한 정책 사건이 묻히게 하지 않는다.

## 7. 공개 계약 및 운영 테스트

`data/state/manifest.json` + `data/state/meta.json.gz` + `data/state/records/<종류>/<버킷>.json.gz`: 수집 이력·버전 원문·조문 비교·정부24 공공서비스·AI 초안 등을 논리적으로는 한 상태로 읽되 Git에는 키별 SHA 버킷으로 나누어 저장하는 내부 원천. 버킷은 작은 결정론적 gzip 파일이며 변경이 없는 버킷은 재커밋하지 않는다. 구식 `data/state.json`은 최초 성공적 분할 저장 후 제거한다.

`site/data.json`: 현재 원천으로부터 매번 생성한 `events[]`와 검증근거 `documents[]`, `relationships[]`, `program_dependencies[]`.

`contracts.py`는 **사건 하나에 실제 변경 문서가 정확히 한 건만 포함되는지**, 모든 변경 조문과 기관 검토 항목이 그 문서의 조문과 연결되는지, 조문 SHA·사업 인용·AI 보조검토 근거가 맞는지 원문 데이터와 대조한다. 하나의 조문이 관련 없는 정책 사건에 포함되거나 원천 근거 없이 기관명이 추가되면 배포가 차단된다.

GitHub Actions는 단일 워크플로에서 **검증, 수집/AI, 단일 사이트 배포**의 책임을 분리한다. UI 코드 push 시에는 기존 공식 원천으로 검증한 뒤 즉시 Pages를 배포하고, 정기·수동 실행에서는 수집과 Gemini 분석을 먼저 수행해 근거 검증·상태 저장 후 최신 스냅샷을 한 번 배포한다. **Pages 동기화 장애가 공식자료 수집과 Gemini 작업 자체를 건너뛰게 만들지 않도록** 수집 작업은 `publish`에 의존하지 않는다. 초기/후속 두 번의 Pages 배포는 제거했다. 배포 작업의 제한은 25분이며 GitHub Pages action 자체는 20분으로 제한한다.

회귀 검증에는 같은 공포번호·같은 날짜로 발표된 서로 다른 법령의 격리, 대표 법령 제목 뒤에 다른 법령의 조문이나 기관이 혼합되는 오류 차단, 지방자치법규의 잘못된 병합 방지, 근거 없는 기관 생성 차단, 직접 규율기관·명시 수행주체·공공사업 인용의 증거 구분, AI 출력 위조 차단, 사용자 목록/모바일 상세 흐름을 포함한다.

## 8. 근거에 기반한 변경 설명과 미리보기

`meaning.py`의 출력 계약은 `change_kind`, `source_check_required`, `before`, `after`, `description`, `focus[]`를 구분한다. `focus[]`는 실제로 바뀐 원문 구절의 앞·변경부분·뒤 문맥을 각각 구분하여 표시하고, 전체 원문은 별도 접기로 남긴다. 그래서 길이가 긴 공통 서두 때문에 신구가 동일하게 보이는 오류를 방지한다. **인용 조문 숫자 수정, 수치 기준 변경, 넓은 범위의 문구 재구성, 단순 표기 정비, 불완전한 종전 원문**을 서로 다른 사건의 특징으로 관리한다. 비교가 불가능한 문서를 근거 없이 기관 업무 변경으로 해석하지 않는다. `parser.py`와 `analysis.py`는 항 번호만 수집된 자료의 완전성을 부정하며, 이전에 저장된 자료는 공개 투영 과정에서 확인 필요 상태를 표시한다.

변경 핵심 상위 3건은 사전 확인된 기관·사업의 업무 검토 근거, 변경 조문의 실질성, 이미 검증된 AI 검토 여부를 반영하되, 단순 인용 번호 수정과 원문 미확보 항목은 후순위로 한다. 검증된 AI 요약만 상세 핵심 카드에 보조 정보로 함께 표시한다.


`analysis.py`의 `spans()`는 원천 차이를 감사하기 위한 기술 데이터이며, 좌우 각 16문자 발췌를 사용자가 읽는 설명으로 재사용하지 않는다. `meaning.py`가 실제 공식 조문의 `before`/`after`에서 **단어 단위 차이, 변경 유형, 전후 비교 표현, 설명 문장, 미리보기 우선도**를 재계산한다.

문장부호·띄어쓰기만 달라진 조문은 별도 표기 정비로 분류하고, 금액·자격·공고 등 변화는 해당 문맥으로 구분한다. 확인되지 않은 법적 효과·실제 기관 업무 이행을 자연어로 단정하지 않는다. 미리보기에 선택되지 않은 나머지 조문과 전체 원문은 상세에서 언제든 열 수 있다. `contracts.py`는 요약과 우선순위를 원천에서 다시 산출해 무근거 표현을 차단한다.

**공포번호·공포일 및 법령 종류가 모두 같아도 여러 법령을 단일 변경 사건에 병합하지 않는다.** 공포 이력은 기록·탐색의 연결 정보이며 기관별 조치 범위를 합치는 근거가 아니다.

## 8-1. 독립 공식 행정규칙 재대조와 PDF 별표

`api.changed_rule_window()`: `admrulOldAndNew` 공식 목록에서 발령일자·행정규칙 종류별 판본 목록을 별도 조회한다. `reconciliation.py`는 기존 `documents`를 실제 공식 ID로 대조하며 수집 창의 완료·실패·신규 발견 수를 영속화하고 누락 ID를 별도 분석 대기열에 등록한다. `annexes.py`는 관련 법령 원문에 명시된 정부 서버의 PDF 별표만 읽고, 디지털 문자·파일/텍스트 해시가 확인될 때만 동일 번호의 별표·서식 조문으로 비교한다. 제정된 연간 행정규칙은 과거 동일 기준이 발견되는 경우에 한해 전년도 공식 문서와 비교한다. 누락된 PDF, 스캔, HWP는 분석 성공으로 둔갑시키지 않는다.

## 9. 공식자료 누적 처리와 데이터 완전성 계약

**GitHub 상태 저장 장애 대응:** 기존 단일 `data/state.json`이 100MB 한도에 도달하면서 공식 수집·AI 결과 저장이 거부되고 Pages 배포가 건너뛰어졌다. `state_store.py`가 이전 상태를 한 번 읽어 **키 해시로 분할된 압축 버킷**으로 이관하고, 이후 변경되지 않은 버킷은 동일한 bytes를 유지한다. `load_state()`는 분할 저장소를 우선 로드하며 모든 버킷을 병합해 기존 계약과 같은 메모리 구조를 반환한다. 누락·손상 버킷은 새 상태로 초기화하지 않고 즉시 실패한다. 상태 저장 성공 후 원래 대형 JSON을 제거하고 GitHub에 변경 버킷 및 `site/data.json`만 반영한다. **공식 문서의 고시 등 누락 문제는 이 저장 문제와 독립된 수집·분석 과제로 유지한다.**



공식자료 1만 건 이상 미분석 상태에서 신구 비교가 계속 지연되지 않도록 **정기 실행 시간대를 두 종류로 나눈다.** UTC 짝수 시각 17분에는 기존 15개 원천 스트림을 순회하되 수집 시간을 최대 150초로 제한하고 나머지 시간을 신구 비교에 배분한다. UTC 홀수 시각 47분에는 원천 색인을 다시 조회하지 않고 기존 미분석 문서 비교만 수행한다. 두 경우 모두 결과는 동일한 `data/state.json`에 누적 저장하며 각각 근거 검증·AI 검토를 수행한 후 공개 사이트에 반영한다. 원천 자료 미확보, 불완전 PDF/HWP 별표, 종류 미분류 문제까지 이 변경만으로 해결됐다고 표기하지 않는다.



`coverage.py`는 **공식 원천 색인과 원문 비교 대기열을 별도 영역으로 유지**한다. 검색 범위를 법령 1종, 행정규칙 6종의 현행·연혁, 자치법규 현행·연혁의 **15개 원천/상태 스트림**으로 분리한다. 최근 7일을 재확인하고 과거 이력은 법령·자치법규 14일, 행정규칙 28일씩 독립적으로 조회하며 공식 API 페이지 제한에 걸리면 해당 기간을 나눈다. 역사적 범위는 절대 날짜 커서로 독립 기록한다. 특정 출처의 날짜 범위 검색이 실패해도 다른 출처의 진도가 멈추지 않으며, 미완료된 해당 날짜 구간은 그대로 보존해 재시도한다.

`fair_work_queue`는 최근 미처리 문서·장기 미처리 문서·실패 문서에 교대로 기회를 배분한다. 새 법령이 계속 발생해도 오래된 문서가 영구적으로 최신순 대기열 끝에 갇히지 않는다. 시간 예산 안에서 처리한 검증 결과만 상태 파일에 저장한다. 진행 현황은 원천별 색인, 부분 비교, 미시작, 재확인, 재확인 유예을 따로 표시한다.

첫 목록은 **전체 / 신규 / 개정 / 폐지 / 영향도 큼**의 5개 빠른 선택으로 단순화한다. 검색은 법령·정책명·소관기관·사업명·변경 항목을 함께 검색한다. 영향도 큼은 원천 근거로 검토 대상 기관이 2곳 이상 확인된 범위를 표시하며 실제 사회경제적 효과의 정량 평가를 주장하지 않는다. 특정 정책 분야만 고정 메뉴로 우대하지 않는다.

본 구조는 실제 공공기관·부처·지자체·교육청 전체의 사업자료 및 고시 첨부표를 확보했다는 의미가 아니다. 자료 접근 범위, 검색 범위, 실패 및 미처리 건수는 구분해 보고한다.

## 10. 공식 공공서비스 탐색 원천 추가

`gov24.py`는 행정안전부의 공식 공공서비스 OpenAPI를 소스로 사용하는 독립 모듈이다. 서비스 목록·상세의 페이지·서비스 ID·원천 기준·소관기관·원문 필드를 저장한다. 기존 `alioplus.py`는 별도의 공공기관 사업 원천으로 유지하고, 두 공급원의 정답을 무리하게 병합하지 않는다.

정책 변경에 연결되는 Gov24 결과는 **공공서비스 검토 후보**로만 생성한다. 정확한 법령·조문 인용 / 법령명 인용을 분리하고 근거 출처 및 서비스별 적용 기준을 남긴다. `gov24_contract.py`가 각 후보의 문서 ID·변경 조문·원천 서비스 ID·실제 소관기관과 인용 원문을 재검증한다. 기존 `institutional_reviews[]`는 근거 검증된 법령 자체의 업무 검토 목록이며, Gov24 탐색 후보는 `public_service_leads[]`로 분리해 조치 의무로 간주하지 않는다.

공식 API는 별도 인증키 `GOV24_SERVICE_KEY`가 필요하다. 미등록 시 서비스 이름/기관을 하드코딩한 가짜 데이터를 만들어 넣지 않고 수집 미설정 상태를 게시한다. 정부24 수혜적 공공서비스 전체가 모든 공공기관의 인허가·규제·공공서비스를 의미하지 않으므로 전체 커버리지라고 표기하지 않는다.

## 11. 남은 과제와 현재 한계

1. 공식 근거의 수집 자체가 불완전하다. 특히 고시의 별표/첨부표, 직전 연도 지원기준, 부처·지자체·교육청 사업문서의 수집 확대가 필요하다.
2. 알리오플러스는 현재 첫 목록 페이지 일부만 수집한다. 전체 중앙·지방 공공부문 사업 커버리지로 오해하면 안 된다.
3. 현재 연결되는 것은 직접 규율기관·명시 수행주체·공식 인용 사업 중심이다. 규범의 변경이 여러 기관에 **암묵적으로** 파급되는 관계를 빠짐없이 판정하는 전국 단위 모델은 아직 완성되지 않았다.
4. 실제 기관 후속 조치 완료·미완료는 공식 실행 근거가 없으므로 판단하지 않는다.
5. 장기적으로 사이트에 큰 `documents[]` 원문이 동봉되는 문제는 증분 데이터 저장과 상세 지연 조회로 개선해야 한다. 현재 구현을 대규모 실시간 운영 플랫폼으로 표기하지 않는다.

이 아키텍처의 목적은 이전 화면의 데이터를 재사용하는 것이 아니라 **공식 원천에서 정책 사건과 기관 업무 영향을 새롭게 생성할 수 있는 재현 가능한 소프트웨어**를 만드는 것이다.

## 고시·공고·지침 수집과 기관별 적용기준

법제처의 공식 행정규칙 API는 `knd=1~6`으로 훈령·예규·고시·공고·지침·기타를 구별한다. 이제 각 분류의 현행·연혁 기록을 독립적으로 수집·재시도하고 공식 종류를 문서에 보존한다. 기존 행정규칙 수집 날짜를 승계하며, 색인됐지만 신구 비교가 안 된 자료는 분석 대기로 표시한다. 고시 별표가 첨부파일로만 제공되면 본문 기준금액을 임의 생성하지 않고 첨부 원문 미분석 상태를 유지한다.

정부24 공공서비스는 실제 기관·사업의 `선정기준·지원대상·지원내용·신청방법·신청기한` 중 검토할 항목을 변경 조문과 연결한다. 서비스 원천에 종전 수치가 존재하는 경우에만 개정 후 기준과 직접 대조하도록 안내하고, 실제 적용 여부는 검토 후보로 남긴다. 공개 데이터 검증은 서비스ID·소관기관·법령 인용·사업 항목·기준 금액을 공식 원문과 다시 대조한다.

정책 상세 첫 화면은 핵심 변경 설명만 표시하고 변경 전후 발췌와 공식 조문 전문은 펼쳐보도록 한다. 공공서비스별 검토 기준은 기관·사업명 아래에 표시하며 근거 문구와 등록 원문은 별도로 펼칠 수 있다.


### 대량 수집 보호와 연도별 고시 비교

공식 행정규칙 6종을 현행·연혁별로 조회하되, 수집 시간 예산을 넘기면 확인한 기록은 보존하고 미조회 종류의 커서를 유지한다. 다음 실행은 마지막 미조회 종류부터 계속 처리한다. 고시가 포함된 행정규칙 분석 대기열은 공식 종류별로 균등하게 교대하며, 제목에 연도가 들어가는 연례 규정은 국가법령정보센터가 문서화한 현행(nw=1)과 연혁(nw=2) API를 각각 사용해 전년도 같은 제목의 근거를 찾는다. 이 기능은 중위소득 등 특정 고시를 하드코딩하지 않는다.



## Incremental source and public projection (v2)

- `state_store.py` reads legacy v1 records without loss, then writes a v2
  manifest. Official clauses are identified by their canonical SHA-256
  fingerprint; identical text+metadata across editions references one block.
- New clause contents are added to immutable compressed content packs under
  `data/state/content/`; a previous pack is never edited during a later run.
- Document metadata, version-to-clause references, findings, public services and
  AI results use independently updated deterministic `records_v2/` buckets.
- In-memory `state["versions"]` retains the original complete source contract.
  Collectors and verified comparison algorithms do not see storage references.
- The Pages build verifies full evidence before writing `site/catalog.json`,
  `site/sources.json` (lazy search index), and
  `site/details/event-<id>.json` (loaded only after click). The former
  `site/data.json` monolith is removed; generated snapshots are not committed.
- Completeness audit remains explicit: successful migration and validation
  never imply that every official source or public-program impact was found.
